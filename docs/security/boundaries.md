Dashed edges are opt-in: `--llm-proxy` (on in this repo's GitHub Actions review and revise workflows), `--egress`, and the writes of the [shadow Approver](../autonomous-loop.md#approver-shadow-mode) (this repo's GitHub Actions workflow; it never merges, approves or labels). Without the first two the model token sits in the sandbox's noexec tmpfs and egress is open.

One opt-in feature sends data from the host itself: the [difficulty probe](../cli.md#decision-models) (`TASKCELL_DECISION_PROBE=1`) posts issue text to a decision-model endpoint from the host process, so neither the sandbox nor `--egress` and `--llm-proxy` cover it, and it skips white-label runs unless set to `all`. The sandbox is the blast radius, not the host. Secrets reach the sandbox through an in-RAM tmpfs file (POSIX-quoted, never in `docker inspect` or on disk), never via argv. Host subprocesses use argument arrays, never shell strings. `.env` is a template only; no secrets live in the repo. The base image is pinned by digest; SIGINT/SIGTERM destroy live sandboxes and a host concurrency limit caps how many run at once. Generate an image SBOM with `pnpm sbom` (needs syft). `taskcell run --egress` confines the sandbox to an internal docker network whose only route out is a proxy sidecar that tunnels just the allowlist (anthropic/github/linear/registries), so even a process that ignores the proxy has no route out.

`TASKCELL_OWNER_LABEL=<id>` labels every container and network with `vanguard.owner=<id>`, so a CI job can remove its own leftovers: first the containers with `docker ps -aq --filter label=vanguard.owner=<id> | xargs -r docker rm -f`, then the egress network with `docker network ls -q --filter label=vanguard.owner=<id> | xargs -r docker network rm`, which Docker refuses while a container still uses it. `xargs -r` skips the command when nothing matches, so a clean job does not fail its `after_script`.

## Verify gate

The verify command (and the visual-proof command) run through one gate exec, `gateExec` in `src/sandbox/gate-exec.ts`: a non-login shell that reads only the root-owned `/etc/profile`, so agent-owned `$HOME` dotfiles and the agent-writable secrets file cannot change the result (#1180). A test fails if a gate module calls the sandbox without it (#1187). Untracked workspace files do not appear in the PR diff, so before the command verify deletes every `node_modules` and reinstalls from the lockfile (pnpm, npm or yarn, detected from the lockfile): a planted `node_modules/.bin/<runner>` that exits 0 is replaced and cannot forge a PASS (#1183). A failed install fails the verify. Remaining limits: a project without a lockfile is not reinstalled; `TASKCELL_VERIFY_REINSTALL=0` turns the reinstall off (offline hosts); other untracked files the command executes (a generated script, a build output outside `node_modules`) are still agent-writable, and the reviewer sees only the diff. The install itself still trusts state the agent can write: the package store and cache under its `$HOME`, an ignored installer config (`.npmrc`, `.pnpmfile.cjs`, `.yarnrc.yml`) and an untracked lockfile. Closing those needs the gate to run as a different user with a fresh `$HOME` (#1196).

## Copy-back

Changed files leave the sandbox through one module, `src/sandbox/copy-back.ts`, and its path policy decides what may come out. `.git`, `node_modules` and `.pnpm-store` are pruned at the source: the `tar` inside the sandbox excludes them, so they never reach the host. Before anything is copied, a `find` inside the sandbox counts the workspace; past 2 GiB or 200,000 files the run stops and nothing is committed. That `find` runs as the agent and cannot see into a directory the agent made unreadable, while the `tar` runs as root, so the stream has its own hard byte cap: copy-out is killed once it passes the ceiling plus about 1 KiB of tar overhead per file. CI config (`.github/workflows/`, `.github/actions/`, `.gitlab-ci.yml`, `.gitlab/**.yml`, or a `.github`/`.gitlab` symlink or file standing in for those directories) is dropped on the host, logged when the agent changed it, and checked again on the final diff before the commit. A file the agent deleted is deleted in the worktree too: the sandbox lists the paths that are in its "vanguard baseline" commit and gone from the workspace, and the host removes only relative paths that stay inside the worktree (no `..`, no symlink escape), never `.git`, CI config or a pruned name. Deletions are applied before the copy, so a file that became a directory (or the reverse) does not abort it. Without a baseline commit, or when listing fails, the deletion sync is skipped with a warning. Files go in and out as a tar stream over `docker exec`, because `docker cp` cannot write into or read from the tmpfs mounts of a read-only rootfs. A GNU tar exit code of 1 is accepted only when every warning says a file changed or was removed while it was read (a watcher still running); any other failure fails the copy.

## Host LLM proxy

`taskcell run --llm-proxy` (also on `watch`) keeps the real Anthropic credential out of the sandbox entirely. A trusted reverse-proxy sidecar holds the credential; the sandbox is handed only a random **per-run nonce** as `ANTHROPIC_AUTH_TOKEN` and points `ANTHROPIC_BASE_URL` at the sidecar. The sidecar validates the nonce, swaps in the real credential (OAuth `Authorization: Bearer` or `x-api-key`), and is the only thing that talks to `api.anthropic.com`.

Just add the flag; the key lives in the host env (never the sandbox) and Docker must be running:

```bash
export CLAUDE_CODE_OAUTH_TOKEN=...                       # host key, stays in the sidecar
taskcell run --linear TES-1 --llm-proxy                  # Claude credential held by the sidecar
taskcell watch --label vanguard --llm-proxy              # same, for the watch loop

export ZAI_API_KEY=...                                   # z.ai key, also stays in the sidecar
taskcell run --linear TES-1 --provider zai --llm-proxy   # z.ai credential held by the sidecar
```

The same nonce/sidecar pattern now also covers Codex/OpenAI when Codex is selected with `--llm-proxy`: a separate OpenAI sidecar holds the real OpenAI key, the sandbox gets a nonce as `OPENAI_API_KEY` plus a base URL pointed at that sidecar, and `api.openai.com` is dropped from the sandbox allowlist alongside `api.anthropic.com`. With `--provider zai`, the primary sidecar instead forwards to `api.z.ai` (the z.ai key as a bearer key), `api.z.ai` is dropped from the allowlist, and the sandbox gets the same `ANTHROPIC_BASE_URL`/nonce shape — so the same nonce/sidecar invariant covers z.ai too.

A Codex **ChatGPT subscription** (`CODEX_AUTH_JSON`) is covered by the same pattern: its own ChatGPT sidecar holds the real OAuth credential, and the sandbox is handed a placeholder `auth.json` (per-run nonce as `access_token`, a run-bound refresh placeholder, a synthetic `id_token` carrying only the non-secret account id + plan type) with the model base URL and the `CODEX_REFRESH_TOKEN_URL_OVERRIDE`/`CODEX_REVOKE_TOKEN_URL_OVERRIDE` pointed at the sidecar. The sidecar is the only party that ever presents the real refresh token to `auth.openai.com` (refresh-token rotation makes a second holder fatal — see [the credential-isolation spike](../research/codex-credential-isolation.md)), and `chatgpt.com` is dropped from the sandbox allowlist. A `CODEX_AUTH_JSON` that is not a ChatGPT-plan credential (e.g. a legacy `--with-api-key` file) has no sidecar to front it and is still forwarded into the sandbox; the hub run warns when that happens, and the CLI refuses to start under `--llm-proxy`.

**Refresh failures and rotation.** What the sidecar tells the cell and the run log when the token refresh fails:

- **Refused** — the IdP answers 400/401/403 with a known OAuth refusal code (`invalid_grant`, `refresh_token_reused`, `refresh_token_expired`, `refresh_token_invalidated`, or another `refresh_token_*`). The cell gets a 401 with that code (an unknown `refresh_token_*` becomes `refresh_token_refused`) and a fixed message per code that says to sign in again (`codex login`).
- **Anything else** — 429, 5xx, a 400/401/403 without such a code (a WAF page, `invalid_request`), a timeout, an unreachable IdP, a redirect, an oversized or unreadable response. The cell gets a 502 with a fixed cause and "retry the run", never sign-in advice.

Nothing the IdP wrote is relayed: its response only selects between fixed strings. Only the ChatGPT sidecar's stderr goes to `docker logs` (its per-request lines on stdout do not, and the other `--llm-proxy` sidecars start exactly as before). Only a real exchange with the IdP is logged, so replies replayed inside the backoff or after the per-run cap cannot grow the log. At teardown (the relay and hand-back run once however often teardown is asked for; only a failed container removal is retried, and the container stays tracked for the signal sweep until it is gone), the host destroys every sandbox first (so a cell still running cannot rotate the token after the read-back), then the proxy; it strips control characters (C0/C1, U+2028/U+2029, bidi overrides) and caps each relayed line, and prints each distinct line in the run log: a refusal as an `ERROR` (with CI or hub advice appended), any other failed exchange as a `WARNING`, and neither if a later refresh succeeded. If the container's log cannot be written, the run warns at start that sidecar errors will not be relayed.

When the IdP rotates the refresh token, the host reports it in the run log and reads the rotated credential back from the sidecar's tmpfs before the container is removed, also on SIGINT/SIGTERM. Only `access_token`, `refresh_token` and `last_refresh` are merged, and only into a copy that still holds the refresh token the run started with, so a newer `codex login` and the other fields are never clobbered:

- **This process:** its own `CODEX_AUTH_JSON` is updated in memory, so a later run of the same process (`taskcell watch`, a second stage) starts with the live token.
- **Local run:** the file the credential came from (`CODEX_AUTH_FILE`, else `$CODEX_HOME/auth.json`, i.e. `~/.codex/auth.json`) is rewritten atomically (a fresh `O_EXCL` temp file renamed over it), mode 0600. A symlinked `auth.json` is resolved once and its target gets the same checks. The write is skipped if the file changed while it was being prepared; Codex takes no lock, so a `codex` writing in the last instant can still lose its write.
- **CI** (`CI`/`GITHUB_ACTIONS`): there is no host file and Taskcell never writes repository secrets. The log and the job summary say the stored `CODEX_AUTH_JSON` is now stale and must be re-set by hand.

Not updated, and named in the log: a `CODEX_AUTH_JSON` exported in another shell, and one saved in the hub credential store (Settings → Credentials) — save it again from the auth file. When no local file holds the token the run started with (a hub run on a stored credential), nothing is written and the log says, without naming a path on the host, that the stored copy must be saved again. A run that is killed outright (SIGKILL) or reaped by `taskcell gc` loses the rotated token: sign in again. **Concurrent runs:** each run's sidecar holds its own copy of the same refresh token and the IdP rotates on use, so the first run to refresh invalidates the others (their refreshes are refused and they must sign in again) and only the first rotation can be handed back. Run one Codex-plan run at a time per credential; an API key has no such limit.

The flag **implies `--egress`** and additionally **removes `api.anthropic.com` from the sandbox's allowlist**, so the sandbox has no direct route to Anthropic — its only path to the model is through the sidecar. The invariant: the real key never enters the sandbox; a leaked nonce is useless beyond the run and never reaches Anthropic. `--llm-proxy` now protects the Claude, Codex/OpenAI, and z.ai provider keys. Cursor is not yet proxied — selecting `cursor` with `--llm-proxy` still injects `CURSOR_API_KEY` directly into the sandbox (a stable Cursor base-url proxy is planned).

`TASKCELL_SANDBOX_READONLY=1` makes the sandbox rootfs read-only (`--read-only`, with `/workspace`, `$HOME` and `/tmp` as writable tmpfs — see `sandboxSecurityOpts` in `src/sandbox/limits.ts`), so an agent cannot write anywhere else, e.g. into tool directories it later executes. It is **opt-in**, with or without `--llm-proxy`/`--egress`: the tmpfs mounts live in RAM and are charged to the sandbox memory limit (8192 MB by default once opted in), which a smaller host or a large monorepo cannot afford, so the rootfs stays writable unless the variable is set (an empty value or `0` keeps it off). With no memory limit at all (`TASKCELL_SANDBOX_MEMORY_MB=0`) the tmpfs mounts are unbounded by a cgroup and the run warns. Every `--egress`/`--llm-proxy` run logs a `sandbox:` line saying whether it is on.

See [smoke-tests/codex-openai-proxy.md](../smoke-tests/codex-openai-proxy.md) for the current verification status, a zero-cost negative preflight check, and a controlled live runbook that walks through the Codex/OpenAI proxy preflight and a read-only `review-pr` smoke run when active OpenAI billing is available.

The `review-pr` and `review-mr` commands read code from the change's real base branch and repository instruction files and skills from the repository's default branch. Default-branch guidance applies even when a release branch carries different review rules; an unavailable default branch fails the review.

## Hub credential store marker

Once the hub's credential store (`credentials.enc.json` in the hub config directory) is read or written under `TASKCELL_HUB_SECRET`, the hub records that in `credentials.keyed` beside it, so a `credentials.key` plus store planted in the config directory later is not read, re-keyed under the secret or trusted while the marker is present. The marker's content is never used as a key. The marker sits in the same directory as the store, so it guards only against an actor who can write files there but cannot delete them. The marker can itself be deleted, so an actor who can delete files there is not stopped (keep the directory write-protected). For an actor who can only create files, a planted marker is new availability harm: the hub refuses to read a disk-key store beside a marker, and with no usable secret it refuses every save while a marker is present, even when `credentials.enc.json` is absent (with its own message, also shown in Settings). It never deletes the marker in that case. The resulting lock-out is accepted, because a create-only actor gets no access to credentials from it, only a refused save until the operator removes the marker; an actor who can also delete the store can lock the hub out anyway. Each refusal names `credentials.keyed` as the file to remove (from the hub config directory) to read the store on `credentials.key` again. Keep the config directory write-protected.
